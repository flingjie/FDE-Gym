03 / Mechanisms

关键执行机制

三条链决定系统可信度：发现回合如何把自然语言变成证据事实；事务如何避免重复模型调用和半提交；实机 doctor 如何判断当前 Codex 客户端是否满足 strict-mode 门槛。

发现回合

问题先成为事件，Customer 只看 customer capsule，Evidence Tracker 只看公开 turn + graph。Patch 经图不变量校验后才进入事实源。

受限模型调用

每次 invocation 都是 fresh、ephemeral、read-only workdir；原始输出、stderr 和文件先过 canary scan，再过 strict schema。

可恢复提交

模型完成后先原子写 prepared journal，再追加事件与 effects。崩溃恢复读取 journal，不会重新向模型提问。

04 / Trust model

三角色安全边界

安全性不依赖 prompt 里的一句“不要泄露”，而依赖字段级构造、严格 schema、capsule 类型判别、隔离子进程、canary 扫描与公共投影的连续防线。

Customer

  • 评分、画像、证据图与 hints

06 / Design tensions

应保留与应收敛

“看起来重复”不等于“应该抽象”。安全边界中的显式重复通常有价值；真正需要收敛的是会让 production 与 doctor、事务与直写路径产生行为漂移的重复事实源。

应收敛
Strict Codex 参数策略存在两份

codex-runtime.ts:73-82 与 capability-probe.ts:443-453 独立维护，doctor 可能认证与生产不同的隔离配置。最简方案是一份纯参数策略，不引入 registry/factory。

应收敛
Orchestrator 同时暴露 prepare 与直接 append 包装器

CLI 正确使用 prepare* + command transaction；若生产调用者使用 run*/submit* 直写，会绕过 journal、结果重放与 effects。生产提交路径应唯一。

应保留
三角色 wrapper 的显式骨架

虽然都执行 firewall → invoke → sanitize，但 capsule 信任模型和后置验证不同。动态统一容易把白名单变成配置，降低 fail-closed 可读性。

应保留
运行时与角色层的双重 sanitize

运行时覆盖 stdout/stderr/output file；角色层覆盖 fixture 或其他 AgentRuntime 实现。两层防护服务不同攻击面，是有意 defense-in-depth。

应保留
最小 RunState 与完整 RunAggregate fold

前者服务纯阶段门，后者服务恢复与 replay。它们处在不同抽象高度，应以契约测试绑定，而不是强行合并。
