# Current Node Catalog — FDE-Gym Runtime (Wave 0 / G0-03)

A **Node** here is a unit of work the runtime executes: an agent invocation, a guard/validation, a deterministic computation, or a projection. Each entry records the candidate Node ID, phase, kind, input, output, the implementing file+function, the domain events it produces, and its recovery/resume capability.

This catalog maps the **current code** (as of Wave 0) onto the shared candidate vocabulary from the Wave 0 plan. It does not invent code: where a seed ID has no current equivalent it is marked `not-yet` or the nearest function is named.

## Legend

- **Kind** — `agent` (model invocation through the `AgentRuntime`), `deterministic` (pure compute, no model/no wall-clock/no randomness), `guard` (validation/rejection that can throw; a deterministic predicate that gates progression), `projection` (deterministic learner-safe read model). There are **no `human` nodes in the runtime**: the learner participates only as the *command boundary* (their prose arrives inside `ask`/`submit-*` command arguments and is Zod-validated there), never as a runtime-executed work unit.
- **Recovery/resume** — every mutating node runs inside `executeCommandTransaction` (`src/core/command-transaction.ts`), the single commit API. A `prepared` command journal is finished on restart **without re-invoking a model**; a `committed` journal with a matching `requestHash` returns the stored result. Agent calls run *outside* the run lock; deterministic/guard nodes are pure and re-derivable by `foldRunAggregate`.

## Implicit vs. distinct-function nodes

**Already distinct functions/modules** (clean Node boundaries):
- `customer.invoke` → `answerDiscoveryQuestion`; `evidence.invoke` → `extractEvidence`; `coach.brief.invoke` → `validateProblemBrief`; `coach.review.invoke` → `runFinalReview`/`sampleFinalReview`.
- `evidence.patch.guard`/`evidence.patch.apply` → `applyEvidencePatch` (one function; guard and apply are the same call).
- `brief.structure.guard` → `validateBriefStructure`; `brief.support.guard` → `calculateSupportRatio`.
- `challenge.select` → `selectScenarioEvents` (+ `buildTriggerContext`); `hint.grant` → `requestHint`; `score.compute` → `calculateScore`/`buildScoreInput`/`buildScoreProvenance`/`computeMeasuredCapability`; `profile.apply` → `updateLearnerProfile`/`applyProfileAttemptEffect`; `replay.project` → `projectReplay`/`foldRunAggregate`/`projectPublic`.

**Inline in the orchestrator** (no distinct function — candidates for future extraction):
- `discovery.question.accept` — step 1 of `prepareDiscoveryTurn`.
- `customer.project` — the sanitize+validate tail of `answerDiscoveryQuestion` (guard) plus the separate replay-time `projectPublic`/`projectReplay` (projection). There is **no single "customer.project" function**; the two concerns live in different modules.
- `evidence.pending` — the catch block of `prepareDiscoveryTurn`.
- `discovery.metrics.compute` — `computeDiscoveryMetrics`, called inline at step 6.
- `challenge.inject` — `prepareChallengeInjection` (a distinct function, but coupled to `challenge.select` via `submitDesign`).
- `challenge.response.guard` / `challenge.all-answered.guard` — both inside `prepareRespondToChallenge`.
- `pitch.structure.guard` — inside `preparePitch`; `solution.accept` — inside `prepareSolutionDesign`.
- `brief.support.guard` composite (the `supportRatio >= 0.75 && structure.passed` gate) — step (d) of `prepareFramingGate`.
- `judgment.guard` — cross-cutting: `sanitizeAgentResult` + per-role `validate*Output` are shared, but there is no single "judgment guard" step in the pipeline; it is embedded in each agent wrapper.

## Candidate IDs with no current equivalent

- `run.complete`, `run.abort`, `run.start-retry` — schema + phase legality only, no producer/use-case. Terminal phases `COMPLETED`/`ABORTED` and `RETRY_READY` are declared in `RUN_PHASES` but never reached. `retry` currently requires `REVIEW` (not `RETRY_READY`) and emits no `run.completed`.
- No `human` node exists: learner actions are the command boundary, not runtime work.

## Integration notes (for Phases/Edges catalogers)

- `evidence.patch.guard` and `evidence.patch.apply` are **one function** (`applyEvidencePatch`) — decide at integration whether to keep one Node or two.
- `customer.project` currently spans two modules (sanitizer tail in the agent wrapper; `projectPublic`/`projectReplay` for replay). A canonical Node ID must be fixed.
- `challenge.select` + `challenge.inject` share a single command transaction in `submitDesign` (`commandId` and `${commandId}:inject`); `solution.accept` is glued to them in the same use case.
- `coach.review.invoke` fans out to `sampleFinalReview` + `aggregateReviews` when `samples > 1`; the aggregated path omits the per-invocation `judgment` envelope on `review.completed`.
- `judgment.guard` is a per-role cross-cutting concern, not a pipeline stage; provenance is separate (`src/core/judgment.ts`).
- Seed IDs `brief.structure.guard`, `coach.brief.invoke`, `brief.support.guard` are all sub-steps of the single `prepareFramingGate` transaction.
